# Demo script

A five minute walkthrough that shows the system doing the thing it claims to do,
in an order that builds an argument rather than listing features.

Every query here has been run and produces output that fits on one screen.

## Before recording

Start the database and open three things: a terminal, the dashboard and the API
docs.

```bash
make psql
```

In a second terminal:

```bash
make dashboard
```

In a third:

```bash
make api
```

The dashboard is at `http://localhost:8501` and the API docs at
`http://127.0.0.1:8000/docs`.

Terminal setup that makes a recording readable:

- Increase the font size until the widest output below fits without wrapping.
- `make psql` already turns the pager off, so results print inline.
- Clear the screen between beats so each result stands alone.

Do not run `EXPLAIN ANALYZE` live. The measured numbers are already in
`docs/query_optimization.md`; show that file instead.

## Beat 1: the claim, in one sentence

Say it before showing anything:

> This is a recommendation engine where PostgreSQL does the recommending.
> Feature engineering, the similarity matrix, candidate generation, filtering,
> scoring and ranking are all SQL. Python generates the data, orchestrates the
> pipeline, measures the result and serves it.

## Beat 2: the scale it runs at

```sql
SELECT
    (SELECT count(*) FROM users)                 AS users,
    (SELECT count(*) FROM products)              AS products,
    (SELECT count(*) FROM orders)                AS orders,
    (SELECT count(*) FROM order_items)           AS order_items,
    (SELECT count(*) FROM user_interactions)     AS interactions,
    (SELECT count(*) FROM mv_product_similarity) AS similarity_pairs;
```

One row: 10,000 users, 2,000 products, 1.2 million interactions, 98,850
similarity pairs.

> The dataset is synthetic and generated by this project, because no real one
> was available. That matters, and I will come back to it.

## Beat 3: what the recommender actually sees

Pick user 2 and stay with them for the next four beats.

```sql
SELECT c.category_name, p.subcategory, count(*) AS events
FROM user_interactions AS i
JOIN products   AS p ON p.product_id  = i.product_id
JOIN categories AS c ON c.category_id = p.category_id
WHERE i.user_id = 2
GROUP BY 1, 2 ORDER BY events DESC LIMIT 5;
```

Mice, gaming accessories, PC components, keyboards, laptops.

> This user was generated from a `pc_builder` persona, but that label is never
> read by the recommender. All it gets is this behaviour.

## Beat 4: the feature layer

```sql
SELECT left(p.name, 32) AS product, f.view_count AS views, f.cart_count AS carts,
       f.purchase_count AS buys, f.interaction_score AS score, f.decayed_score AS decayed
FROM mv_user_product_features AS f
JOIN products AS p USING (product_id)
WHERE f.user_id = 2
ORDER BY f.decayed_score DESC LIMIT 5;
```

> The score is a weighted funnel: a purchase counts ten, a cart five, a wishlist
> three, a view one. The decayed column is the same sum with an exponential half
> life, so a basket abandoned last week outweighs one abandoned last year. That
> is all SQL, in `views.sql`.

Point at the laptop row. It is the best evidence in the demo that the decay is
real rather than decorative:

| product | raw score | decayed | retained |
| - | -: | -: | -: |
| Pantheon Precision Mouse | 30 | 20.63 | 69% |
| Meridian Creator Laptop | 19 | 17.19 | 90% |

> The laptop has a much lower raw score but ranks third, above products scoring
> 20 and 25, because its engagement is far more recent. It keeps 90 percent of
> its score where the mouse keeps 69 percent. That is the half life doing the
> work, and it is why the ranker uses the decayed column.

## Beat 5: the taste model

```sql
SELECT category_name, interaction_score, category_affinity, preference_rank
FROM mv_user_category_preferences
WHERE user_id = 2 ORDER BY preference_rank;
```

Electronics 0.60, Gaming 0.40.

> Affinity sums to 1 per user, so the ranker can blend it without rescaling.
> Notice it does not match the raw score ratio exactly, because affinity is
> built from the decayed scores. If those two matched, the recency weighting
> would not be doing anything.

## Beat 6: the similarity matrix, the centrepiece

Product 134 is a laptop.

```sql
SELECT left(product_name, 38) AS product, brand, similarity_score, common_users, relationship
FROM get_similar_products(134, 6);
```

Keyboards, a monitor, mice, then another laptop.

> This is item to item collaborative filtering, computed as a single self join
> over the feature table. It is cosine similarity over engagement vectors, so
> dividing by both norms removes popularity. Without that, the bestseller
> co occurs with everything and becomes everybody's neighbour.
>
> Nothing in these product descriptions connects a laptop to a trackball mouse.
> That link exists only because the same 347 people engaged with both. The
> `common_users` column is the evidence, so the matrix is auditable rather than
> a black box.

## Beat 7: recommendations, with reasons

```sql
SELECT recommendation_rank AS rank, left(product_name, 30) AS product, price,
       recommendation_score AS score, left(recommendation_reason, 58) AS why
FROM get_recommendations(2, 5);
```

> One function call runs a twelve stage CTE pipeline: anchors from history,
> neighbours from the matrix, purchased products excluded, five signals
> normalised and blended, ranked, explained.
>
> The reason is not a label chosen afterwards. It is generated by a CASE over
> the same normalised components that produced the score, so it names the signal
> that actually won.

The `why` column above is truncated to keep the table on one screen. Follow it
with this so the full explanation is readable, which is the line worth having on
camera:

```sql
SELECT recommendation_rank AS rank, recommendation_reason FROM get_recommendations(2, 3);
```

> "Customers who bought Sable Everyday Low Profile Keyboard 6 also bought this,
> and 33 other items in your history point to it." That names a real product the
> user owns, and the count is how many of their history items independently
> pointed at this candidate. Agreement across a history is stronger evidence than
> one coincidence, and the explanation says so.
>
> The category rows cite their rank inside the aisle, so no two rows on the shelf
> carry the same sentence.

## Beat 8: proof it is personalising

This is the most convincing thirty seconds in the demo.

```sql
SELECT u.persona, left(r.product_name, 34) AS product, r.category
FROM users AS u
CROSS JOIN LATERAL get_recommendations(u.user_id, 3) AS r
WHERE u.user_id IN (2, 3, 5)
ORDER BY u.user_id, r.recommendation_rank;
```

Nine rows in three clean blocks: a PC builder gets a laptop, a monitor and a
keyboard; a console gamer gets a controller, a console and a game; a fashion
shopper gets a denim jacket, trainers and jeans.

> One database, one function, three completely different and internally
> coherent shelves. The recommender recovered that structure from behaviour
> alone.

## Beat 9: cold start

```sql
SELECT recommendation_rank AS rank, left(product_name, 30) AS product, strategy,
       left(recommendation_reason, 40) AS why
FROM get_recommendations(9, 3);
```

Every row says `trending_cold_start`.

> User 9 has no history at all. There is no separate code path for this: cold
> start changes which sources contribute candidates, and the same scoring and
> ranking code runs over whatever arrives. Trending here is decayed popularity
> multiplied by momentum and weighted by a Bayesian smoothed rating, not a raw
> purchase count.

Then show it never fails:

```sql
SELECT count(*) AS rows_returned, min(strategy) AS strategy
FROM get_recommendations(10000000, 10);
```

> An unknown user id is not an error. It falls back to trending, which is the
> right behaviour for an anonymous visitor.

## Beat 10: the business rule that is never negotiable

```sql
WITH recs AS (SELECT product_id FROM get_recommendations(2, 20)),
     owned AS (
         SELECT oi.product_id FROM orders AS o
         JOIN order_items AS oi USING (order_id)
         WHERE o.user_id = 2
     )
SELECT (SELECT count(*) FROM owned) AS already_owned,
       (SELECT count(*) FROM recs)  AS recommended,
       (SELECT count(*) FROM recs JOIN owned USING (product_id)) AS leaked;
```

42 owned, 20 recommended, 0 leaked.

> The exclusion happens in SQL, not in the application, so a caller that forgets
> to check cannot get it wrong. Out of stock products are filtered the same way,
> at serving time, so a product withdrawn one second ago stops being recommended
> on the next request.

## Beat 11: latency

```sql
\timing on
```

```sql
SELECT count(*) FROM get_recommendations(2, 10);
```

Around 6 to 20 ms against a 1.2 million row interaction log.

> That is possible because everything expensive was computed offline into
> materialized views. The similarity build aggregates millions of co occurrence
> pairs and takes 30 seconds; a request touches a few hundred indexed rows.

## Beat 12: the numbers

Switch to the dashboard, Model evaluation tab. Or open
`docs/evaluation_results.md`.

| Metric | Popularity | Collaborative | Hybrid |
| - | -: | -: | -: |
| Precision@10 | 0.0141 | 0.0722 | 0.0756 |
| Hit Rate@10 | 0.1340 | 0.4373 | 0.4680 |
| Users served | 1.0000 | 0.7920 | 1.0000 |

> Three things here. First, the popularity baseline is in the table at all,
> because it is trivial to build and deceptively strong, and a recommender that
> cannot beat it is not paying for its complexity. This beats it 5.4x on
> precision.
>
> Second, pure collaborative filtering serves only 79 percent of users. It
> returns nothing for cold users. The hybrid serves everyone.
>
> Third, this is a temporal split. The entire pipeline is rewound to the cutoff
> and every materialized view rebuilt, so no future event is visible to any
> feature or similarity score. Building the matrix on all the data and holding
> out a random slice gives beautiful numbers that mean nothing.

Then open `docs/query_optimization.md`:

> Indexing took the per request anchor lookup from 96.8 ms to 0.4 ms with a
> covering index. Those are measured by dropping the index, timing, restoring it
> and timing again, not estimated.

## Resume bullets

All figures below are measured and reproducible with `make evaluate` and
`make benchmark`.

- Built a SQL first e commerce recommendation engine in PostgreSQL, with feature
  engineering, item to item collaborative filtering, candidate generation,
  scoring and ranking implemented entirely in SQL across 3,400 lines; Python
  handled data generation, orchestration, evaluation and serving.
- Implemented item to item cosine and Jaccard similarity as a single self join
  over 380,000 user product features, producing a 98,850 pair matrix in 30
  seconds using log damped weights, per user activity capping and a triangular
  join.
- Beat a popularity baseline by 5.4x on Precision@10 and 3.5x on Hit Rate@10
  under a leak free temporal evaluation that rewinds the whole pipeline to the
  split point and rebuilds every materialized view.
- Cut recommendation latency to roughly 6 ms against a 1.2 million row event log
  using covering and partial indexes, verified with EXPLAIN ANALYZE: the per
  request anchor lookup dropped from 96.8 ms to 0.4 ms.
- Generated a behaviourally realistic 1.2 million interaction dataset with 12
  persona archetypes, planted complement pairs and a power law demand curve, so
  the recommender had genuine structure to recover rather than noise.
- Exposed the engine through FastAPI and Streamlit, with 55 tests running
  against a live database, including a check that users of the same persona
  receive more similar recommendations than users of different personas.
